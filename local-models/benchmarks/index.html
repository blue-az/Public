A result is only as reproducible as the stack that produced it. Where a value was not recorded, this page says so rather than leaving it out.

Why this page exists

A benchmark result without its protocol cannot be checked, and a protocol restated in prose drifts away from the runs it describes. Every definition here is generated from the file the harness and the internal dashboard both read, so there is one source rather than three descriptions that agree until they do not.

What is not defined here yet

Screening. Nothing on this page says how a model enters or leaves the roster, what battery screens it, or what it must clear to be ranked. The current three were chosen by a screening pass that exists only as narrative, and the models ruled out are not listed anywhere a reader can check. That is the next piece of work, and until it lands, treat the roster as given rather than as justified.

Placement on older rows. Results from before 22 Sep 2026 ran without a placement proof, so for those rows it cannot now be established whether the model was on one card, two, or partly in host RAM. New rows carry the evidence; old ones carry the gap.

What L0, L1 and L2 mean — and why there is no L3

They are instruction levels of the same task against the same postcondition. Only the prompt's specificity changes: never the fixture, never the grading. A level measures how much the model has to infer, so a model that passes L2 and fails L0 has not become less capable — it has been told less.

LevelPrompt isWhat the model must doExample prompt
L2fully specifiedNumbered steps naming the file, the exact strings and the verification. The model executes rather than infers."1. Read runbook.md... 2. Under the heading '## Staging' only, replace the single line '2. Run: restart the service' with '2. Run: restart the service --force'..."
L1stated plainlyOne clear paragraph naming the file and the intent, without step-by-step or exact literals. The model decides how."In runbook.md, the step 'Run: restart the service' appears under Production, Staging and Development. Change only the Staging one..."
L0obliqueHow a colleague would actually ask. No file named, no literal given, the goal implied. The model must infer the target, the exact edit and the success condition."Staging needs the force flag when we bounce it. The other environments must stay as they are."

The postcondition does not soften as the prompt does. At L0 the grader still requires the exact byte match it requires at L2, so an under-specified prompt is graded against a fully specified answer. That is the intended difficulty and also its main confound: a level measures instruction inference AND exact-form luck together.

On the Z13, gemma4:26b scores 6/6 on ambiguous-anchor at both L2 and L1 and 0/6 at L0, with no modified line appearing in any trace and half of those failures ending in context truncation. It does not do the edit at all rather than doing it wrongly.

There is no L3, and there never was. The name used to appear as “Fusion L3”, where L3 meant a third difficulty tier on the Fusion axis — a separate benchmark family with its own tasks, fixture and grader. Sitting next to L0/L1/L2 it read as a rung above L2, which it never was. That family is now TennisAgent Fusion, versioned v1 and v2, since versions are what actually distinguish the packets. Its artifact paths still contain l3 and are deliberately unchanged, because every evidence root and source link on file points at them.

The E9 standard is two legs, not one

The quality leg and the wall-clock leg run over different task sets, in separate runs, to separate evidence roots. They share exactly one task. A quality count therefore does not vouch for a time recorded beside it, and warm means include failed trials unless a row says otherwise.

Read it with
  • An 18-cell denominator cannot distinguish a true 75% pass rate from 100%.
  • Denominators are printed because they are not interchangeable between hosts.
  • Warm trials are graded too. The reported mean includes failed trials unless the row says otherwise, so a mean can contain time spent producing a wrong answer. Report per-trial pass/fail beside every mean.
  • Never use the aggregate wall mean in wall-RESULTS.md: it combines both tasks and includes the cold trial.
  • Decode tok/s is not this measurement and does not predict it.
  • csv-summarize-repair needs n>=6 warm trials before an ordering between two models is readable. Measured 2026-09-25 on a cleared single 3090, its within-model spread reaches 84% of its own mean between identical trials (12.8-23.6s around a 19.75s mean), which is wider than most differences being claimed. At the default n=4 (3 warm) the draw picks the winner - an n=3 reading put qwen3.6 and qwen3.8 2.1x apart on this task, and a paired n=6 run put them 1.6% apart with overlapping ranges. constant-and-callers does not have this problem; its ranges separate cleanly at n=3. Do not report a long-task ordering from 3 warm trials.

Pinned across every E9 definition: tag=e9pin, num_ctx=16384, temperature=0.8, thinking=off, ledger=none. Everything else runs as the model ships, so a ranking here ranks each model at its shipped defaults, not at its best.

A cell has three outcomes

Pass and fail are not enough, because a harness fault and a wrong answer look identical in a pass count. Both produce a number rather than an error.

  • pass — graded correct, with every proof below satisfied
  • fail — graded incorrect AND every proof below satisfied. Only this counts as evidence about the model.
  • unproven — any proof missing or failed. Not a model result, not poolable, and never rendered as a score. Recorded with its raw trace for forensics.

A failing cell is promoted to fail only when all five proofs hold:

ProofWhat it establishes
dispatchthe call happened — non-zero tokens, a resolved model identity, no no-dispatch state
scopethe graded fixture is byte-identical apart from the model's own intended edits
placementthe model ran where the row says it ran, from the host's own telemetry
graderthe failure survives a grader spot-check. A deterministic grader that has never been boundary-tested against negation, synonyms and section headings is a suspect, not an oracle.
timingthe trial completed without timeout, and the recorded time excludes harness bookkeeping

Default to unproven. Promoting unproven to fail requires the proofs, not an argument that the model probably was wrong. Mixed results across a roster are the signature of an unproven cell class, so triage the instrument before interpreting the spread.

One harness across three point releases, run weeks apart: historical 0.85.1, testbench 0.86.0, z13 0.86.1. Drift is normal and cannot be prevented — work that spans months will span releases. Recording it is the requirement; freezing it is not.

Bridge run. The cheap way to settle a suspected-material change: re-run one cell class on both versions on ONE host, small n, and compare. A bridge run answers the question for the whole corpus. Absent one, do not assume a version delta explains a result — and do not assume it does not.

What may never be pooled

Pooling is forbidden by default: results may only be compared within one definition, on one host.

  • e9-standard-l2 &mdash; e9-extension-l1 &mdash; e9-extension-l0
  • z13-max390 &mdash; testbench-native
  • testbench-native &mdash; testbench-hybrid
  • e9 local rows &mdash; Haiku staged control
  • fusion-v1-retained &mdash; fusion-v2
  • blind-read rounds with each other &mdash; since each is one observation
  • different model digests or tags

Counts accumulate over different corpora with different denominators. A rate computed across them is arithmetic, not a measurement. Quality rank transfers between chips; speed rank does not. The Z13 penalty against the 3090 varies by task and reverses, so no single multiplier exists.
