One-Minute Snapshot

This product is a session-first tennis motion capture system. The user starts on the Apple Watch, the iPhone keeps a local archive and can relay batches onward, and the Mac backend can ingest, mirror, and query sessions for an operator or browser viewer. The owner should treat the session as the main record; swings are derived output layered on top of captured motion, not a separate source of truth.

The important boundary is that the product is split across surfaces. The watch depends on HealthKit approval and an active workout session before capture is stable; the phone can keep data locally and fall back to USB Mode when the Mac is not reachable; and the backend and export surfaces shown in the snapshot do not include an in-app authentication gate. That makes this a product about capture, storage, and controlled movement of tennis data, not a generic dashboard.

The Product Shape

Think of the product as one tennis session moving through three layers. The Apple Watch is the recorder. The iPhone is the relay and local archive. The Mac backend is an operator-managed extension that can accept data, store it, and expose live or read-only views to a browser viewer.

The owner should not flatten those layers into one app. Some paths are core to capture, some are fallback or export paths, and some are optional depending on deployment. That matters because the product can still preserve a session locally when the backend is absent, but that does not mean every surface is equally safe or equally complete.

Sessions are the main record. Swings are derived from captured motion and should be read as interpretation, not the original event. That distinction matters later when you decide how much weight to give the analytics output.

The Session Path

On the watch, the user starts a session and the device prepares the workout and motion capture path first. The phone receives sensor batches, stores them locally, and can relay them to the Mac when a configured host responds. If the Mac is not reachable, the phone remains useful as a local archive and can later move data through USB Mode or the export flow.

The Mac backend accepts session traffic, can mirror live batches to a viewer, and can answer session and swing queries. One important wrinkle is that the backend does not only wait for an explicit session start: a sensor batch can also create backend session state. That makes the live path more flexible, but it also means later chapters need to be precise about what started the session and where the record actually lives.

What The Snapshot Supports

  • The watch requests HealthKit approval at startup and starts the workout and extended runtime before motion capture; continuous capture should not be promised without that prerequisite.
  • The watch resend path queues stored batches and marks the session transferred afterward, so it is replay-based rather than delivery-confirmed.
  • The iPhone probes only two fixed hosts on one port, then falls back to USB Mode if neither responds.
  • The iPhone keeps saving sessions and batches locally even when the backend is unavailable.
  • The export control starts a local web listener on port 8080 and serves the phone archive as a download.
  • The backend exposes ingest, relay, health, list, and detail surfaces directly, and a sensor batch can begin backend session state without a prior start.
  • The live backend uses stronger swing settings than the packaged defaults and examples.

What Is Strong Here

Three strengths stand out. First, the product keeps capture local before it tries to be clever, so a session does not vanish just because the Mac is absent. Second, the system makes the capture, archive, backend, and export surfaces visible enough that an owner can reason about them as separate responsibilities. Third, the product keeps the session record and derived swing output distinct enough that later chapters can discuss analytics without pretending it is the raw record.

The weakness inside those strengths is that flexibility creates boundary risk. The same architecture that gives you local fallback, export, and live backend access also gives you more places for drift, exposure, and ambiguity to appear.

The Capture Gate

Treat session start as a chain of gates. The watch must have the right permission and workout state before motion capture can be trusted, and the phone must be ready to receive or at least retain the data locally. That means the owner should read the start of a session as a readiness check, not as proof that every sample has already reached a durable destination.

Where Session Data Lives And What Counts As The Record

One-Minute Snapshot

Session data lives in layers, not in one place. The watch keeps the first local copy so a session can be retried later. The iPhone keeps the owner's local archive and can also expose or erase it. When the Mac backend is reachable, it keeps its own retained copy and may add derived swing or shot records. Transfer, resend, and export all create more copies; the reviewed evidence does not prove that any one of them becomes the only record.

For the owner, the key question is not where data exists at all, but which copy is treated as the record, which copy is a duplicate, and which copy may be safely removed.

Mental Model

Think in layers. The watch is the first storage point and keeps batches so capture can be retried. The iPhone is the owner's local archive and remains useful even when the backend cannot be reached. The backend chapter owns operator duties and queries; here the storage fact is simply that a backend copy can exist independently of the phone archive. These layers can overlap, so a session may exist on more than one of them at once, and moving data does not automatically erase the earlier copy.

The practical rule is simple: watch storage protects capture, phone storage protects the local archive, and backend storage protects the operator-side retained record. That is enough to make the product resilient, but it is not enough to prove a single final authority.

How It Works

On the watch, stored session batches are queued for resend later, so recovery is based on retrying stored data rather than on a delivery-confirmed handoff. On the iPhone, batches and sessions are saved locally first, and the phone can still fall back to its local archive path when the Mac is not available. On the backend, incoming sensor batches are written into stored session and raw motion records, and derived swing results or shot records can also be created from that flow.

One lifecycle wrinkle matters to owners: a backend batch can create session state even when the explicit start message never arrived. That means the record trail can begin from more than one path, which is useful for recovery but awkward for cleanup and audit. The export chapter owns the mechanics of moving data out; here the key point is that export adds another copy, while Clear Database removes only the phone-local archive.

Mental Model

Think of this chapter as the system's exit controls for session data. Normal capture produces local records first; from there, the product can retry movement from the watch, move the archive out through the phone, or remove the local copy entirely.

These are not interchangeable. A resend tries to recover transfer. An export creates a new copy outside the phone. Clear Database removes the current local copy. The owner's job is to decide which exits are allowed in practice and who is responsible for the copy after it leaves the device.

How It Works

On the watch, resend walks through the stored batches and queues them through the watch connection, then marks the session as transferred afterward. That means the retry path is based on queueing, not on a confirmed delivery signal. If the user taps resend more than once, the behavior can race its own transfer flag.

On the iPhone, the app checks only two known backend addresses. If neither responds, it switches to USB Mode and continues saving locally. When the operator starts the HTTP export surface, the phone offers the local database file as a download to any caller that can reach it. The evidence does not say who should receive that file, so the owner has to set the containment rule.

Clear Database is separate from export. It deletes the phone-local session and raw motion records and then compacts the file. That is a cleanup action, not a recovery action.

How The Numbers Are Produced

The running backend does not use the same swing settings as the reusable detector defaults. In the live path it uses a larger motion buffer, a higher motion threshold, and a wider minimum gap between counted swings. When real-time detection is turned off, the session-end path records a zero shot count instead of pretending a swing total was measured live. The result is useful output, but still output: it is a calculation layered on top of the session, not a second source of truth.
