What It Does

Operator Control Plane is a trust infrastructure for AI coding work. It doesn't execute code, manage repos, or orchestrate agents. It records who claimed what, what evidence supports it, who verified it, and how much it cost — and enforces rules about when those records can be trusted.

The core loop is simple:

  1. Open a task
  2. Agent makes a claim ("I fixed the retry logic")
  3. Agent attaches evidence (test output, file hashes)
  4. A different identity verifies it
  5. Doctor checks the ledger for consistency

Everything else — sessions, usage accounting, handoff briefs, delegate-brief, enrolled authority — is built around this loop.

Architecture

It's a Python CLI with SQLite as the durable store and YAML as the compatibility surface. The design is straightforward:

SQLite → canonical history. YAML → compatibility view. Doctor → audit. Broker → enrolled authority.

What's well-designed

✅ Append-only SQLite with SHA-256 event links. The durable history can't be silently rewritten. Events are linked by per-record hashes, protected from UPDATE/DELETE by triggers. This is the right call for an audit trail.
✅ UID-isolated verification. A verification only counts if the verifier's OS UID differs from the claim author's. This is a real boundary, not a paper one — two agents under one Unix user are one identity.
✅ Reconciliation requires explicit acknowledgment. When the authority store changes, the system doesn't silently adopt the new state. It asks the operator to confirm. This prevents "mysterious" state transitions.
✅ Closeout is provisional. A later negative verifier write can reopen a task. This is honest about the nature of verification — it's not a one-way gate, it's a continuing signal.
✅ Local-first by default. The product works immediately with ./operator init. Enrolled authority is opt-in, not the default. This matches the actual use case of a single developer or small team.
✅ Doctor never executes. The audit tool is read-only. It validates paths, bytes, hashes, and identity. It does not run --verify-cmd. This is an important separation — the checker is not the executor.

What's less well-designed

⚠️ YAML + SQLite duplication is a maintenance burden. The YAML projections are gitignored "compatibility views" that can be rebuilt from SQLite. They serve no durable purpose — they're neither backup nor authoritative. They exist because someone wanted a human-readable format but also wanted SQLite's integrity. Neither format is the source of truth; SQLite is. The YAML adds complexity without adding durability.
⚠️ The command surface is sprawling. ~23 subcommands across tasks, claims, evidence, verification, sessions, usage, briefs, handoff, and delegation. For a tool that should be approachable, this is a lot of surface area. The navigation helps (local loop first, admin second), but the cognitive load is real.
⚠️ "Harness" naming is misleading. A harness is a routing profile (which agent CLI to use), not a trust authority. The name invites the false inference that the harness itself has any authority. "Lane" or "profile" would be less confusing.
⚠️ Enrolled authority is half-built. The broker is installed as a service, the CLI resolves enrollment against it, and operator-admin handles lifecycle. But "no production ledger is enrolled yet" and "initial installation must execute a root-owned staged copy." It's a real system, but it hasn't been exercised in production. The gap between "installed" and "enrolled" is meaningful.

Strengths

1. The trust model is honest

Most verification systems pretend that a signature or a checkmark is sufficient. Operator's model is more nuanced:

  • A claim is not a fact — it's a statement tied to a task
  • Evidence is not verification — it's retained proof, hashed and stored
  • Verification is not final — it's a signal that can be negated later
  • Doctor is not a fix — it's a continuing audit

These distinctions are easy to blur in practice. Operator makes them explicit in the data model and the CLI surface.

2. Lane economics are well-thought-out

The billing model — cost is the driver's price, not the author's — is a real insight. If Claude charges $20 and Claude Code charges $5 for the same work, the ledger should reflect that. This matters for teams that use multiple agents.

The "cheap-lane" principle — transcript chores (summaries, rehydration) should run in cheap seats — is practical advice that most teams skip.

3. The separation of concerns is clean

Each path has a clear purpose and a clear trust level. They don't blur together.

4. Session-derived IDs over role labels

Using claude-019KSo7K instead of claude-builder for --by, --assign, and --review is the right call. Session IDs are stable for the session; role labels drift. This prevents identity confusion in multi-session environments.

Weaknesses

1. The product does too much

Operator started as a ledger for tracking claims and evidence. It has grown into a system that also handles:

  • Task management
  • Claim registration with typed assertions
  • Evidence attachment and hashing
  • Session tracking and cost accounting
  • Usage import from multiple harness providers
  • Handoff brief generation
  • Headless delegation across 6+ agent CLIs
  • Study plans with phase catalogs
  • Checkpointed dogfood runs
  • Local A/B comparison
  • Enrolled authority with a broker
  • Root-only administration

That's not a ledger anymore. That's a platform. The question isn't whether it's useful (it is) — it's whether all of this belongs in one tool. The command surface reflects this bloat: ~23 subcommands, each with their own flags and mental model.

2. The "harness" abstraction is leaky

The harness system catalogs 12 profiles at operator init. It claims to support Claude Code, Codex, Gemini, Grok, and others. But the documentation is honest: "That they are cataloged is a fact about the source. That each provider's CLI still behaves as this product expects is not shown here."

This is a real risk. Agent CLIs change. Their session formats change. Their APIs change. The harness system needs active maintenance that the current documentation doesn't reflect.

3. Dogfood is dangerous

The dogfood runner is "a privileged run" bound to "installed machine paths and a release digest." Treating it as a retry button "hands out a powerful command with less slack than people expect." This is understated — dogfood is effectively an arbitrary execution engine wrapped in checkpointing. The recovery path is narrow on purpose, but the entry point is powerful.

Risks

1. The local ledger is the single point of failure

Everything important lives in .operator/ledger.sqlite3. It's gitignored. There's no automatic backup. The documentation says "this is not an off-machine backup or an adversarial tamper-proof boundary." It's a SQLite file on a writable disk. If the disk dies, the audit trail dies with it. This is fine for a development tool, but it means the "trust record" has a very real vulnerability.

2. Enrolled authority is aspirational

The broker path is the "serious" version of this system — the one with real role separation, host-managed trust, and root-only administration. But:

  • No production ledger is enrolled yet
  • Real-host privilege proof remains issue #7
  • Provisioning and rollback safety are "not proven from source alone"

So the most important feature is untested in production. The local ledger works, but the local ledger is the "advisory" path. The gap between "works locally" and "works enrolled" is the biggest gap in the system.

3. The trust model depends on Unix UIDs

The UID-isolated verification model is strong in theory — but it depends on genuinely distinct OS users. In containerized or CI environments, UIDs can be shared or mapped. The documentation acknowledges this ("the CLI does not provision those users or containers") but the risk is real: if two "different" agents run under the same UID, the verification is meaningless.

4. The system is domain-neutral in name only

Operator claims to be "domain-neutral" but is deeply optimized for AI coding work. The claim types (test_passes, file_exists, model_output), the harness system (agent CLIs), the session tracking (coding sessions), and the brief generation (handoffs between agents) — all of this is coding-specific. "Domain-neutral" is aspirational marketing, not architecture.

Operator's unique position: It's the only system that combines a full ledger lifecycle (task → claim → evidence → verification → session → usage) with lane economics, session-derived identity, and an enrolled authority path. The others are narrower. Operator is the most complete system in this niche.

Verdict

Operator Control Plane is a well-designed trust infrastructure that has outgrown its original scope. The core model — claims, evidence, verification, doctor — is sound. The separation of concerns (local ledger vs. enrolled authority, builder vs. verifier, audit vs. execution) is clean. The lane economics and session-derived identity are real insights that most systems miss.

Its weaknesses are real too: the command surface is sprawling, the harness system needs active maintenance, the enrolled authority is untested in production, and the local ledger is a single point of failure. The "domain-neutral" claim is aspirational.

Bottom line: If you need a trust record for AI coding work, this is the best system I found. If you need a fleet orchestrator, look at harmony. If you need doc anchor verification, look at claims-ledger. If you need parallel task distribution, look at open-tui-orchestrator. But for tracking who claimed what, what evidence supports it, who verified it, and how much it cost — Operator is the most complete tool in this space.

Recommendation: Stay on the local ledger unless you have a real need for enrolled authority. The local path is well-designed and works immediately. The enrolled authority path is important but untested — treat it as a future investment, not a current requirement.

Open Questions

These are questions I have about the system after reviewing the source. They're not resolved by the documentation.

  1. What happens when the SQLite file grows beyond practical size? Append-only is great for auditability but terrible for storage. Is there a pruning or archival mechanism? The documentation doesn't say.
  2. What is the actual backup strategy? The SQLite file is gitignored. The YAML is gitignored. The documentation says "back up canonical history, not the projections." But how? Manually? Cron? The tool doesn't seem to include a backup command.
  3. How does the broker handle concurrent operators? The broker is a "restricted Unix socket" that "ties requests to the connecting peer." But what happens when two operators try to reconcile at the same time? What about the "rebuilds a healthier state" scenario mentioned in the docs — is that a real risk?
  4. What is the migration path from local to enrolled? The documentation says enrollment is "not a generic switch" and requires host preflight. But if someone starts with the local ledger (the documented default), what's the actual migration path? Is there a command? A procedure? The docs don't say.
  5. Why is dogfood a separate system from study? Both are "privileged runs." Both have checkpointing. Both have narrow recovery paths. What's the conceptual difference? The documentation treats them as separate but doesn't clearly articulate the distinction.
  6. Is the A/B comparison tool useful? It compares two local OpenCode arms. The documentation calls it "narrow" and "intentionally small." But is it actually useful, or is it a solution looking for a problem? The docs don't say.
  7. What happens when a harness profile's format changes? The usage import system reads session logs from Claude Code, Codex, Gemini, etc. These formats change. What's the update process? Is there version detection? Graceful degradation? The docs don't say.
  8. Should closeout be truly final? The current design says closeout is provisional — a later verifier write can reopen the task. This is honest, but is it useful? In practice, does this ever happen? Should there be a "final closeout" that cannot be reopened?
