How It Works

A supported run starts on the Watch. The player chooses a mode, starts capture, and the Watch begins collecting motion and producing live feedback. That data goes to the iPhone relay, which shows connection state and forwards batches over a fixed local network path to the Mac backend. The Mac backend turns incoming batches into shot records and session feedback.

That chain is fragile in the places an owner cares about. Supported capture depends on the Watch's health and workout permissions, and the source does not establish a graceful denial path. If the relay drops, the current batch can be lost rather than queued. If the backend reconnects, the live session view starts fresh instead of recovering durable history. The readiness number shown back to the player is derived feedback, not a measured physiology signal.

Power state, Wi-Fi state, and whether the Mac backend is present on the expected local network become part of the setup story.

When a relay drop loses data

The lossy part is the one owners tend to underestimate. In the current path, failed relay sends are not held for later resend, and the watch batch is cleared after the send attempt. Put together, that means a disconnect can erase unsent samples rather than parking them safely until the connection returns. This is not just a backend concern: it changes how the operator interprets a temporary drop during a session. If the relay breaks while the player is still swinging, the safe assumption is that the in-flight batch may be gone, not waiting in a recovery buffer. The only automatic retry described in the reviewed material is a periodic connectivity check once the link has already been established, which is a check on reachability, not a durable resend path. So the practical boundary is strict: reconnect manually, then continue only after readiness is rechecked, because the missed batch may never come back.

For example, if the watch has started and the player hits several shots, but the iPhone loses the Mac backend connection midway through the exchange, the operator cannot treat that gap as temporary storage. The supported path today is restore the relay and continue, not restore the relay and replay what was missed.
