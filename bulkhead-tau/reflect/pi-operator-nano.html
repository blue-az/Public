Mental Model

Think of the product as a Pi extension package with a carrier-neutral client and a local target registry that binds to an external Operator ledger. The owner decides policy and acceptable risk; the operator uses the Pi command surface; the reviewer is the model or harness label used for review bundles; the verifier is a separate Unix identity for distinct-identity review runs; and the implementer is the delegated harness target. The command registry is the real surface, not one file pretending to be everything. It is ordered so orientation comes first, then confirmed writes, then optional or authority-bearing paths.

How It Works

The extension binds to the external ledger through an explicit contract or a sibling Operator checkout, so the boundary is visible before any later workflow starts. The command surface is ordered with read-only orientation first, which helps a reader get bearings, but that ordering is only a convention and does not itself prove a permission model. Once the operator moves beyond orientation, the product separates delegation routing, review bundles, and privileged verifier launch into different authority paths. Popup stays in the background as askpass launch plumbing.

How to read the warning

The next-step warning should be read as a conservative hint, not as a verdict that the work is complete. The reviewed evidence shows that the warning is triggered by specific stale patterns, such as wording that already says a claim is verified, repeated handoff guidance after a handoff already exists, or terminal prompts about claim or evidence work. That boundary is easy to miss if you want a simple yes-or-no answer. One-Minute Snapshot

This chapter is about the three write paths that can change the external Operator ledger: creating a claim, attaching evidence, and closing out with a handoff. They are related, but they are not the same action. Claim creation is gated by the current live session and task context, evidence attachment binds to a locator and does not make the claim verified by itself, and handoff only changes the follow-up field when the draft actually contains a Next action section. This is built from the code, so it shows what the product does today, not what you may intend it to mean; that part is yours to confirm.

What You Should Be Able To Explain

  • Explain the difference between a claim write, an evidence attachment, and a handoff closeout in the external Operator ledger.
  • Describe which live gates must exist before a claim write can proceed, and how evidence and handoff choose what they affect.
  • Tell the difference between a confirmed write and a failed attempt that may not have been cleaned up.
  • Decide which parts of this write lane match the policy you want and which parts need correction.

How to Think About the Three Write Steps

Three separate moments

Treat claim, evidence, and handoff as three different write moments against the external Operator ledger. They are related because they often happen in sequence, but they do not do the same work. A claim creates the record that says, in effect, this task is being asserted into the ledger. Evidence attachment adds supporting material to that record. Handoff closes the loop by updating the follow-up field, but only when the draft includes a Next action section. Thinking of them as one generic save action hides the real boundaries and makes it easy to assume one step accomplished another.

Why the claim gate is the tightest

The claim step is the one most closely tied to the live session and the current task. That is the step where the product insists on the active operating context before it will let the write proceed. The practical effect for an owner is simple: claim creation is not a loose note-taking action that can happen later from anywhere. It depends on the task being live and on the session that is currently carrying the action, so the system is using the present operating context to decide whether the claim should be allowed at all.

That matters because it makes claim creation the first real commitment in the write lane. If the live context is missing, the write does not belong to the claim path. If the context is present, the claim can go forward as a guided write. The reviewed evidence does not establish a broader product-wide authority model here, so the safe reading is narrower: claim creation is intentionally anchored to the live task moment, and that anchor is what keeps it from becoming a casual background write.

Evidence does not mean verified

Evidence attachment works differently. It records evidence, but it does not turn that attachment into verification by itself. The owner consequence is important: adding proof is not the same thing as changing the claim’s status. You can attach a screenshot, log excerpt, or other locator-based evidence to support a claim, but that action alone does not certify the claim as verified. The evidence remains evidence; the verification meaning is separate.

A useful way to picture this is a claim that says, “We believe this issue is real,” followed by evidence that shows why the belief is justified. The evidence strengthens the record, but it does not collapse the remaining review or verification step into the attachment itself. That separation is what keeps evidence from being mistaken for an automatic seal of approval.

Handoff is the closeout write

Handoff is the closeout step. It is narrower than a full rewrite because it only changes the follow-up field when the draft actually carries a Next action section. If that section is missing, the handoff does not get to overwrite the follow-up text as if nothing mattered. For an owner, this means the handoff write is structured around explicit closeout content, not around a free-form attempt to replace whatever follow-up already exists.

A concrete example makes the difference clear. Suppose an operator creates a claim for a broken export, attaches evidence that shows the failure, and later prepares a handoff draft. If the draft includes a Next action section that says to recheck the export job after deployment, that is the part that can update the follow-up field. If the draft omits that section, the handoff may still be a written step, but it does not have the right shape to change the follow-up record. That is the boundary that keeps closeout from becoming a vague replacement for the whole task history.

What Happens During Each Write

These three writes share one important trait: each one is gated before it can mutate the external Operator ledger, and each one has a different target. The owner should read them as separate operating paths, not as a single save action with three labels. That distinction matters because the checks that open the path, the thing each path changes, and the condition for calling the write successful are not the same.

Claim write

A claim write does not start from a blank prompt. It begins only when the live interface is present, the current task record exists, and the action can be attributed to the active session. Only after those pieces are in place does the path preview the write and ask for confirmation. In other words, the claim flow is not just about having permission in the abstract; it is about having the right live context in front of the operator at the moment the ledger update is about to happen.

For the owner, that means a claim cannot be treated as a background update that will find its own way through later. If the session context is stale or the task record is missing, the claim path stops before the ledger change is attempted. A practical case is an operator returning to an old screen after the session has moved on: the write should not proceed until the current live context is restored and confirmed. The reviewed evidence does not establish the full external claim lifecycle or the wider supervision policy, so the safe boundary here is the gate itself, not a promise about every downstream state the ledger may support.

Evidence attachment

Evidence attachment works from the locator outward. The path resolves the evidence location first, then decides which claim to bind to. In normal use, it points to the latest unverified claim, or to the latest claim overall if there is no unverified one available. In edit mode, it can instead target a specific claim, which makes the attachment step more precise when the operator is correcting or supplementing an earlier write. That selection rule is the opposite of a claim-first workflow: the evidence path does not begin by asking which claim should be verified.

The consequence for the owner is easy to miss but important: attaching evidence does not itself change verification status. It records evidence against a claim, but it does not turn that attachment into a verified claim. So if an operator attaches a screenshot, note, or file to a claim, the claim remains in whatever verification state it already had until a separate verification step changes it. The evidence flow therefore carries record value without claiming to settle the claim on its own. A good example is an edit-session correction where evidence is attached directly to a specific older claim; the attachment is useful, but it is not the same thing as verification.

Handoff

Handoff is the draft-first closeout path. The draft cannot be empty, the write is confirmed before it runs, and only a draft that actually contains a Next action section can overwrite the follow-up field. That keeps handoff from behaving like a free-form overwrite of whatever follow-up text happened to be there before. The path is structured because the follow-up field only changes when the draft supplies the section that owns that change.

For the owner, this means handoff is best understood as a controlled closeout rather than a generic end-of-task note. If the draft lacks a Next action section, the follow-up field should not be expected to change. If the draft is empty, the path does not even get to the point of making the overwrite decision. A useful scenario is a handoff draft that summarizes the work but forgets the Next action section: the closeout can still be acknowledged as a draft, but the follow-up field stays untouched.

What the Reviewed Evidence Confirms

Claim writes are not free-floating

The reviewed evidence confirms that claim creation is context-bound. Before the write can reach the ledger, the flow checks for a live writing context, the current task record, and session-derived provenance. In plain terms, the system does not treat a claim as something you can emit from nowhere; it wants to know which live session is speaking, which task is being acted on, and who the write is attributed to.

That matters for an owner because it narrows the chance of accidental writes from stale state. If the live session is gone, or the task context is missing, the claim path refuses to proceed rather than guessing. A practical example is a reopened workspace after interruption: the claim shortcut is not supposed to behave like a generic save button; it should stop until the current session and task context are present again.

The boundary is also important. The evidence establishes the gate, but it does not establish the full external ledger lifecycle or any broader supervision policy beyond that live-session requirement. So the safe reading is not “claims are always blocked unless authority is perfect”; it is narrower: this write path requires the current live context that the claim needs, and it is explicit about that dependency.

Evidence attaches to a locator first, not to a verdict

The evidence flow is confirmed to work from the evidence locator first. In normal use it defaults to the latest unverified claim, and if nothing unverified is available it falls back to the latest claim overall. In edit mode, the operator may explicitly choose a claim instead of taking the default. The important fact is that the evidence attachment itself does not change the claim’s verification status.

For the owner, that means evidence and verification are related but separate outcomes. Attaching a screenshot, note, or other evidence does not magically turn the claim into a verified one. It only binds the evidence to a chosen claim after the locator has been resolved. That is a useful restraint because it keeps the evidence trail honest: the system records attachment, not a false impression that verification already happened.

A concrete scenario makes the boundary clear. Suppose the newest claim is still unverified and there is also an older claim in the task. In normal use, the attachment routine reaches for the latest unverified claim first. In edit mode, an operator can point the attachment at a specific claim if the default would be wrong. Either way, the attachment does not promote the claim to verified status. The evidence record is added; the verification status stays what it was until the separate verification step occurs.

The qualifier here is that the exact external verification workflow lives outside this reviewed set. What is confirmed is the selector behavior and the non-verifying nature of the attachment, not the whole lifecycle of how verification is later performed in the ledger.

Handoff only changes the follow-up field when the draft has the right section

The handoff flow is section-guarded. The evidence confirms that the draft must be non-empty, the write is confirmed before it runs, and the follow-up field changes only when the draft contains a Next action section. That makes handoff a structured closeout write rather than a blanket overwrite of whatever follow-up text already exists.

The owner consequence is straightforward: a handoff can be safely narrow. If the draft lacks that section, the system does not treat the whole draft as permission to rewrite the next action. It preserves the existing follow-up field instead of assuming the closeout text should replace it. In effect, the draft has to earn the right to change the follow-up field by including the section the flow is looking for.

For example, an operator might prepare a closeout note that summarizes work done but forget to include the Next action section. The evidence says that omission matters. The handoff can still be drafted and confirmed, but the follow-up field is not overwritten by that draft. That is a useful limit because it prevents a loose summary from accidentally becoming the new next step.

The boundary is narrow but clear: this section proves the guard around the follow-up field, not the policy for every possible handoff style. It does not say the handoff draft is always the preferred closeout path, only that when this flow is used, the section gate controls whether the next-action text changes.

Success requires a clean exit and a readable record id

The shared write helper is conservative about success. It only acknowledges a successful write when the underlying write run exits cleanly and the returned output contains a parsed record id. If the run fails, or the id cannot be read back, the helper reports failure. It does not automatically retry, and it does not claim to roll the write back for you.

That matters because a failed attempt is not the same thing as a clean no-op. The evidence does not prove that nothing reached the external ledger when the run fails; it only proves that the helper will not mark the operation as successful unless the clean exit and record-id parse both succeed. For the owner, that is a warning against reading a failure message as proof that the ledger was untouched.

A simple example: imagine the write command starts, produces partial output, and then exits badly. The helper will not hand back a successful ledger id just because something started. It needs the clean exit and a parseable id before it treats the write as acknowledged. If either piece is missing, the result is failure, not a confirmed write.

The remaining boundary is exactly the one the evidence leaves open. It does not establish any built-in recovery, retry, or rollback guarantee. So the right owner expectation is conservative: a success message means the helper saw a clean write result with an id; anything else is an unsuccessful attempt whose persistence state is not cleaned up by the wrapper itself.

What Is Solid Here

Clear boundaries between write steps

The strongest thing about this write lane is that it does not blur the three write moments together. Claim creation, evidence attachment, and handoff closeout each run through its own gate, perform its own write, and check its own result. That matters to an owner because it keeps the external Operator ledger from behaving like a single catch-all save action. A claim is not silently treated as evidence, and evidence is not silently treated as a handoff. The system makes each step earn its own result.

That structure is valuable even before you care about the details of any one workflow. It gives the operator a clearer expectation of what changed, and it gives the manual a sharper line between one record type and the next. The boundary is also important because it prevents the reader from assuming that a successful action in one lane proves success in another. The claim lane can succeed, while the evidence lane still needs its own locator and the handoff lane still needs its own draft section. Those are separate checks, not one shared promise.

Narrower mutations reduce accidental spillover

The evidence and handoff paths are especially strong because they change less than a generic overwrite would. Evidence attachment binds to a locator and leaves claim verification status alone. Handoff closeout only changes the follow-up field when the draft actually contains a Next action section. In both cases, the write is constrained to the piece of ledger state that the workflow is meant to own.

For an owner, that narrower mutation scope reduces a common failure mode: a user thinks they are adding support material or closing out a task, but the system quietly rewrites more than that. Here, the evidence path can add evidence without pretending that verification happened, and the handoff path can update follow-up text without replacing the rest of the draft. If an operator is attaching a screenshot to a claim, the system is not also reclassifying the claim as verified. If they are closing a task with a handoff note, the system is not rewriting follow-up text unless that note contains the section the flow is looking for. That makes the write behavior easier to reason about and harder to misuse.

The boundary is still real: narrower mutation does not mean no risk. It means the change is more local and therefore less likely to conflate records or overwrite unrelated follow-up text. It does not prove the surrounding ledger model is exhaustive or that every desired cleanup rule exists elsewhere.

Conservative success reporting is a real safeguard

The failure handling is also a strength because it does not dress up a failed write attempt as if the ledger accepted it cleanly. The shared write path only counts success when the underlying command exits cleanly and a record id can be parsed. If either part is missing, the helper reports failure instead of pretending the result is settled.

That conservatism matters because it protects the owner from false confidence. A returned id only means something when the write finished in the normal way. If the command exits badly, or the id cannot be read back, the system does not quietly convert that into a success story. In practical terms, that means an operator reviewing the ledger after a bad attempt should treat the state as uncertain rather than assuming the write either happened or was cleanly rolled back. The manual can say the system was cautious because the evidence supports caution; it cannot promise that a failed attempt left no trace.

A concrete example makes the value clear. Suppose an operator opens a handoff, confirms it, and the write command then fails before returning a usable record id. The system should not report that as a completed ledger write. That restraint is useful because it preserves the difference between a confirmed attempt and a verified result. It also leaves the owner with the right next question: whether the write needs to be checked again, not whether the tool already guaranteed success.

Taken together, these are the solid parts of the lane. The workflows are separated, the mutations stay narrow, and the success check stays strict. Those three qualities do not solve every operational question, but they do make the write lane more legible and less likely to mislead the owner about what actually changed.

How It Works

Delegation starts with a target registry that lives locally and controls aliases plus routing expectations. The owner can use it to express carrier, model, isolation, and routing choices, but the reviewed evidence does not turn those choices into a promise that the target is funded, approved, or safe to use in production. Routing is route-sensitive: if the selected target is already the task’s assigned harness, the parent path stays intact; if the target is unrouted or review-only, the work can become a child task; if the target conflicts with self-delegation or a dual-role case, the flow is refused. The delegate path prefers a brief plus adapter route when the preconditions are met, but task creation, session start, or adapter failure can still force a paste or export fallback. Reviewer, verifier, and implementer are different roles: reviewer is the selected review label, verifier is the authority-bearing launch identity, and implementer is the delegated harness that receives bounded work.

The verifier path is more restrictive than a generic check. The reviewed evidence shows a UI-gated launch, a named verifier bundle, a preflight check, askpass resolution, and a fixed privileged launch built from validated fields. That makes the path policy-sensitive, because the launch decision is explicit and the resulting run still uses the verifier’s permissions and credentials. The popup helper stays secondary here: it is only askpass launch plumbing and does not itself verify claims or define trust.

Verified Facts

The read-only command cluster is presented first, but that is only an ordering convention, not a privilege boundary. That matters because the manual can lead with safe orientation without pretending that the command order itself enforces access control.

Evidence attachment resolves its locator first, then chooses a claim default in non-edit mode, and it does not auto-verify the claim. Handoff writes are structured closeout writes: they need a non-empty draft, they are confirmed before they run, and they only overwrite the next action when that section is present. Successful writes are only acknowledged when the underlying run exits cleanly and returns a parsed record id.

Strengths

This lane gives the owner precise control over who does the work and under which authority. The local target registry keeps routing explicit instead of hidden, the review path keeps reviewer choice separate from verifier authority, and the verifier launch forces a visible approval step before privileged execution. The parent-routed child-task split is also useful because it keeps already-assigned work from being rewritten into a different routing shape just because a delegate command was used. Taken together, those choices make route choice, authority, and fallback visible enough for an owner to govern rather than guess.

Recovery, Limits, and Safe Operation

One-Minute Snapshot

This chapter is the owner’s map for failure handling. It tells you which problems are local to the extension, which belong to the external Operator ledger or host policy, and which can only be handled by retrying or escalating under a different authority. The key boundary is simple: safe reading is not the same as safe recovery, and some advanced paths can still reach external state even when the local launch fails.

What You Should Be Able To Explain

  • Tell a local failure from an external boundary problem before retrying.
  • Know which write paths can be retried, which may already have reached the ledger, and which do not promise rollback.
  • Recognize when delegation or review has crossed into authority-bearing execution.
  • Route setup, write, delegation, and verifier problems back to the right chapter instead of guessing.
  • Avoid assuming that a guarded launch, a duplicate close, or a stale warning proves the underlying state you want.

Mental Model

This chapter is about fault lines, not normal operation. The product starts with safe orientation, but that order is a reading choice, not a permission model. When something breaks, ask first whether the failure is in the local extension, the external Operator ledger, host policy, harness execution, adapter or provider behavior, or verifier and account setup. If the answer is unclear, do not retry blindly: move back to installation for placement and configuration, to orientation for read-only diagnosis, or to the write and delegation chapters for the workflow you were in. The stale next-action warning is also narrow on purpose; it is a pattern check, not a general completion judge.

The diagram places the local extension at the center and shows four different outcomes. A problem that stays inside the local extension can be handled as local recovery. A problem that reaches the external ledger needs an external state check before retrying. A problem that enters review or verifier authority is no longer a local-only issue and should be routed through the correct chapter or authority path. The consequence is that read-only ordering does not tell you where recovery belongs.

How It Works

Write flows are gated and uneven. Claim creation needs a live interface, an active task, an existing task record, and session-derived provenance before it reaches the ledger. Evidence attachment resolves the locator first, then binds to a claim only after that, and it does not auto-verify the claim. Handoff is a structured closeout write: it needs a non-empty draft, asks for confirmation, and only changes next action when that section exists. For all of these, a clean subprocess exit with a parsed record id is the only success signal the wrapper treats as success. There is no built-in retry or rollback guarantee, so a failed write can leave you with unknown persistence and an external state check becomes the next decision.

Delegation behaves like configuration until it becomes a live route. The target registry is local and saved atomically, but a delegate choice can stay on the parent, become a child task, or be refused. Even the adapter path can downgrade to paste or export after a later failure, so the owner should treat the route as conditional. Session close can collapse duplicate close attempts into success, but that only normalizes the close operation itself; it does not prove the first close wrote anything new.

Verifier-related paths are more sensitive. Verify-run is a guarded privileged launch with UI authorization, preflight, and askpass, while popup is only askpass plumbing. Distinct-UID review is an authority path, not a sandbox, and reviewer labels are not the same thing as verifier identity.

Verified Facts

The reviewed evidence establishes a few stable facts the owner can rely on. Read-only commands are presented first for navigation, but that is an ordering convention rather than a permission boundary. The stale next-action detector only flags specific outdated patterns, including repeated handoff guidance and claim or evidence prompts that no longer fit the record. Ledger discovery is contract-bound and fail-closed, and the extension loads as a consumer-local package from the current checkout rather than by wandering across parent directories. The verifier path is explicitly not a sandbox, and the review path keeps reviewer identity separate from verifier authority.

Strengths

The strongest part of the design is that it exposes failure boundaries early. Orientation comes first, write paths confirm before spawn, target routing is saved atomically, and verifier-related paths refuse to pretend they are safer than they are. The product also normalizes some duplicates, like already-closed sessions, which reduces noise when you are recovering from interrupted work. Those strengths help operators reason about failure, but they do not erase external responsibility or make recovery reversible by default.

Accepted Owner Policy

This appendix records the conservative owner decisions applied after review.

  • Read-first ordering is a convention, not permission.
  • The explicit ledger contract is primary; sibling discovery is a checked fallback.
  • Installation is per consumer checkout, not a global backend install.
  • Targets are routing configuration, not execution approval.
  • Parent-routed, child-task, refusal, and fallback delegation outcomes remain distinct.
  • The adapter route is primary when available; paste/export fallback is reported.
  • Advisory reviewer choice and UID-isolated verifier identity remain separate.
  • Verifier identity is an authority boundary, not a sandbox.
  • Failed writes are treated as unknown persistence until external state is checked.

This policy does not claim live host approval, provider support, funding, or sandbox isolation.
